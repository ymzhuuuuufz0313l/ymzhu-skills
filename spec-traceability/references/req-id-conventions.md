# REQ_ID 编码规范

需求追溯号（REQ_ID）的编码与管理约定，用于 spec ↔ 代码双向追溯。

## 编码格式

```
REQ-<模块ID>-<类别><序号>
```

| 段 | 说明 | 示例 |
| --- | --- | --- |
| 模块ID | 模块编号或短名，建议 `M` + 两位数字 | `M00`、`M01` |
| 类别 | 一位字母，见下表 | `F` |
| 序号 | 三位数字，模块内按类别递增 | `001` |

完整示例：`REQ-M01-F001`（模块 M01 的第 1 条功能需求）

## 类别前缀

| 前缀 | 含义 | 使用场景 |
| --- | --- | --- |
| `F` | Functional 功能需求 | 寄存器行为、数据通路、协议逻辑 |
| `P` | Performance 性能需求 | 时序目标、吞吐率、延迟 |
| `I` | Implementation 实现需求 | DFT/scan、可测性、物理约束 |
| `C` | Constraint 约束需求 | SDC 约束、面积/功耗上限 |

常见扩展前缀（按需采用）：`REQ-SYS-###` 系统级需求、`REQ-NFR-F##` 非功能需求。

## 管理规则

1. **只增不删**：需求取消时标记 `deprecated`，不删除 ID、不改写历史。
2. **不复用**：废弃的 ID 永不重新分配给新需求。
3. **唯一性**：全项目内 ID 唯一，用 `check_req_uniqueness.py` 在登记表（CSV，含 `req_id` 列）上校验。
4. **分配**：用 `allocate_req_id.py <模块ID> --category <F|P|I|C>` 取下一个可用序号，不要手填。
5. **传播**：ID 从 spec 文档产生后，沿 文件头 `@requirement` → 行内 `@verifies` → 约束文件交叉引用 逐层传播；每一层只引用，不重新定义。

## 最小落地建议

不需要一次性建全套体系。最小可用组合：

1. 选定一个模块试点；
2. spec 文档中给关键需求编 ID；
3. RTL 文件头加 `@requirement` + `@spec_hash`；
4. 交付前跑一次唯一性检查 + spec hash 比对。
