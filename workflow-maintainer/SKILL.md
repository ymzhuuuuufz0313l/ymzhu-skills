# Workflow Maintainer Skill

## 触发条件

以下情况触发本 Skill：
- 用户说："记录工作流"、"我习惯..."、"以后我..."、"我的工作方式是..."
- 用户说："生成变更日志"、"更新 CHANGES"、"记录变更"
- 用户说："准备回传服务器"、"生成回传清单"、"生成 REVIEW"、"检查变更"
- 用户在修改文件后要求"记下来"、"记录一下"

## 核心原则

1. **所有文件放在打开路径的一级目录下**，不分散到 `.kimi/` 等子目录。
2. **AGENTS.md** 存放项目上下文 + 工作流偏好规则。
3. **CHANGES.md** 存放累计变更日志。
4. **REVIEW.md** 是临时文件，用于服务器回传前检查，可覆盖。
5. **严格记录**：每次修改必须包含文件路径、修改类型、行号范围、修改摘要、修改原因。
6. **文件尾签名（全局强制，适用于所有"代码相关"文件修改）**：见下方「全局文件签名规则」。

## 全局文件签名规则（ymzhu，2026-09-18 起，所有项目适用）

**每次更新文件后，必须在文件末尾按文件类型添加一行注释签名**，内容为 `ymzhu + 日期 + 时间（精确到分钟）`，格式：`ymzhu 2026-09-18 16:30`。

| 文件类型 | 注释写法 |
|---|---|
| `.tcl` / `.pl` / `.py` / `.sh` / `.f` / `.tcl` 脚本 | `# ymzhu 2026-09-18 16:30` |
| `.v` / `.sv` / `.svh` | `// ymzhu 2026-09-18 16:30` |
| `.c` / `.h` | `/* ymzhu 2026-09-18 16:30 */` |
| `.md` / `.html` | `<!-- ymzhu 2026-09-18 16:30 -->` |

规则细节：
- **替换而非累积**：同一文件多次更新时，把末尾签名**替换**为最新时间，不追加多行。
- **无注释语法的文件**（如 `.csv`、`.tar.gz`）不添加。
- 纯二进制文件、生成产物（如 `latest/` 下的运行输出）不添加。
- 该规则已同步写入各项目的 `AGENTS.md`「工作流偏好」章节；若某项目 AGENTS.md 缺失此条，以本规则为准并补录。

## 工作流

### 场景 1：记录工作流偏好

当用户说"我习惯..."或"以后我..."时：

1. 读取当前目录的 `AGENTS.md`。
2. 提取用户描述中的规则，转换为可执行条款。
3. 在 `AGENTS.md` 的"工作流偏好"章节追加该规则。
4. 如果"工作流偏好"章节不存在，先创建该章节。
5. 向用户确认已记录的内容。

**示例规则**：
- "我只在本地改代码，不跑仿真" → 写入：`- 本项目不在本地运行仿真，AI 修改代码后只做代码可靠性检查。`
- "每次改完 RTL 必须更新 CHANGES.md" → 写入：`- 每次修改 RTL 文件后，必须立即更新 CHANGES.md。`
- "回传服务器前要生成清单" → 写入：`- 用户要求"准备回传服务器"时，必须生成 REVIEW.md。`

### 场景 2：记录文件变更

当用户修改文件后要求记录，或本 Skill 被调用时：

1. 读取当前目录的 `CHANGES.md`（如果不存在则创建）。
2. 通过 `diff` 或文件内容对比，确定：
   - 新增文件：列出文件路径和主要功能
   - 删除文件：列出文件路径
   - 修改文件：列出修改的行号范围、修改摘要
3. 按日期分组追加到 `CHANGES.md`。
4. 向用户确认记录内容。

**CHANGES.md 格式**：

```markdown
# 变更日志

## 2026-06-29

### 14:30 - file1.v
- **类型**：修改
- **行号**：45-67
- **摘要**：修复了 xxx 组合逻辑，避免时序违例
- **原因**：用户要求优化关键路径

### 14:45 - file2.sv（新增）
- **类型**：新增
- **行号**：1-120
- **摘要**：新增 yyy 模块，用于 ...
- **原因**：新增功能需求
```

### 场景 3：准备回传服务器

当用户说"准备回传服务器"或"生成回传清单"时：

1. 读取 `CHANGES.md` 和 `AGENTS.md`。
2. 扫描当前目录下最近修改过的文件。
3. 生成 `REVIEW.md`，包含：
   - 变更文件汇总表
   - 关联文件检查清单（AGENTS.md、case_list.txt、filelist 等）
   - 肉眼 Review 建议
   - 回传注意事项
4. 向用户展示 `REVIEW.md` 内容。

**REVIEW.md 格式**：

```markdown
# 服务器回传前检查清单

生成时间：2026-06-29 14:50

## 变更文件汇总

| 文件 | 修改类型 | 行号 | 摘要 |
|-----|---------|------|------|
| file1.v | 修改 | 45-67 | 修复 xxx 逻辑 |
| file2.sv | 新增 | 1-120 | 新增 yyy 模块 |

## 关联文件检查

- [ ] `AGENTS.md` 已更新
- [ ] `CHANGES.md` 已记录
- [ ] `case_list.txt` / `filelist` 已同步（如适用）
- [ ] `check_report.md` 已更新（如适用）
- [ ] 修改记录 / changelist 已同步（如适用）

## 肉眼 Review 建议

1. file1.v 第 45-67 行修改了组合逻辑，请确认是否影响下游模块。
2. file2.sv 是新增模块，请确认接口定义与上层实例化一致。

## 回传注意事项

- 不在本地跑仿真，回传后请在服务器上验证。
- 建议先单独回传并跑一个相关 case，确认无问题后再批量回传。
```

### 场景 4：查看变更

当用户说"查看变更"、"最近改了什么"时：

1. 读取 `CHANGES.md`。
2. 总结最近的变更文件和关键修改点。
3. 如果用户需要，生成或更新 `REVIEW.md`。

## 输出格式

完成任何操作后，按以下格式汇报：

```markdown
已更新工作流记录：

- 操作：{记录工作流 / 记录变更 / 生成回传清单}
- 涉及文件：{文件路径}
- 更新的文档：
  - `AGENTS.md`
  - `CHANGES.md`
  - `REVIEW.md`（如适用）
- 后续建议：...
```

## 注意事项

- **不要创建 `.kimi/` 子目录**，所有相关文件都放在当前工作目录根级。
- 记录变更时，尽量精确到函数/模块/信号级别，方便肉眼 review。
- 如果用户没有说明修改原因，可以标注"原因：未说明"并提醒用户补充。
- `REVIEW.md` 是临时文件，每次生成会覆盖旧内容。
- `CHANGES.md` 是累计日志，按日期追加，不删除历史记录。
