# 工程实测邮件风格（ymzhu 回复/汇报邮件）

> 用途：替 ymzhu 起草对内工程邮件（回复提问 / 汇报实测结果）。风格基准 = 2026-11-18 给 James 的 420B 功耗三问回复。样本库：`samples/`（每封邮件一个 md，按日期命名）。
> 触发词：「写邮件」「回复邮件」「邮件内容」「汇报邮件」「email draft」。

## 起草步骤

1. **收件人语境定位**：读原始提问（转发原文优先）。每个编号问题在草稿里保号回答；无原问时按汇报体组织（见结构）。
2. **数字落锚**：每个论点先落一个实测数字，格式固定——`模块名 + µW 两位小数 + (@速率) + （占总功耗 xx mW 的 yy%）`。数字只来自报表/csv 实测，禁止估算值裸奔；给不出数字的论点降级为「待补测」或删除。
3. **结论先行**：每点第一句给答案（是/否/量级），数字随后作证；机理放在最后一段（寄存器挂共享时钟、ICG 生效/失效、组合逻辑无掩蔽——机理解释放数字背后的"为什么"）。
4. **分解到子块**：凡模块级数字，往下再拆一层子块（如 LONG_ENCODING → OUTPUT/ALIGN/DECODE/DESCRAMBLE），每个子块一句机理。拆不动的写「只剩漏电」这类整链判词。
5. **对比成对出现**：两档速率（3G/4G）、两模式（长码/短码）、两芯片（1V11/1V22）一律成对列；只报单边时明确写缺边原因。
6. **收尾签名**：`Best Regards` + 空行 + `朱彦铭`。

## 硬规则

- 语言：简体中文正文；模块名/信号名/时钟名/工具名保持英文原样（`LONG_ENCODING`、`ICG`、`DCLK_DATA`、`PowerPro`）——不翻译、不加引号。
- 单位纪律：功耗 µW 为主，总额用 mW；占比百分数一位小数；速率档写作 @4G/@3G（正式处可括注实测值如 4.46G）。
- 每封邮件一个主题；多主题拆多封，不合并。
- 收件人用繁体名（彥銘/James）不影响正文简体。

## 骨架模板

```
Dear <名>

<一句背景：今天做了什么/基于什么数据>。

<编号问题逐条>：
(1) <原问复述压缩成一行>？
<结论一句>，实测：<主数字+占比>。
<子块分解 2-4 行，每行：子块+µW+一句机理>。
<可选：整链判词（ICG 生效/只剩漏电）>。

<汇报体则用>：
●<档位> = <µW>（占总功耗 <mW> 的 <%>）

<对比段落：增量拆解成 2-4 条编号结论，每条含量化占比>

Best Regards

朱彦铭
```

## 样本迭代纪律

- ymzhu 提供新邮件 → 存 `samples/YYYYMMDD_<主题>.md` → 对照本文件核对哪条规则被印证/违反 → 修订规则并升版本号（文件尾签名）。
- 样本中与本规则冲突的写法：样本为准（他的手就是标准），改规则不改样本。

## 边界

- 只管邮件正文起草；日报/CHANGES/站点文章各有专门 skill，不混用。
- 敏感数字（未发布规格）按 USER.md 口径：对外分享避免出现项目代号。
